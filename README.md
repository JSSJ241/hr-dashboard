# HR Operations Dashboard

Внутренний дашборд для аналитики найма и стоимости HR-процессов.

## Что уже есть

- расчёт внутренней и внешней стоимости найма;
- средняя стоимость на принятый оффер и time to hire;
- сравнение вакансий по полной стоимости;
- аналитика офферов и причин отказов;
- анализ текучести и причин увольнений;
- управление отделами и актуальной численностью для корректного расчёта текучести;
- общий реестр активных сотрудников с фильтрацией по отделам;
- автоматическое уменьшение численности при увольнении и увеличение при найме;
- контроль участия в опросах и список сотрудников с повторными пропусками;
- ручной журнал проведённых опросов с датой, дедлайном и комментарием;
- создание волны сразу из общего реестра: выбор отдела и отдельных сотрудников;
- проактивные карточки HRBP со сроками, ответственными и результатом контакта;
- импорт настоящих данных о сотрудниках, волнах и участии через CSV;
- помесячная динамика расходов;
- план-факт стратегических HR-метрик;
- месячные KPI;
- редактирование данных и экспорт CSV.

## Структура

Проект состоит из трёх связанных страниц:

- `index.html` — стоимость найма, вакансии и HR-метрики;
- `turnover.html` — текучесть, причины увольнений и отделы риска;
- `surveys.html` — участие в опросах и работа с повторными пропусками;
- `supabase/turnover_schema.sql` — таблицы `departments` и `terminations`;
- `supabase/employee_roster.sql` — реестр сотрудников и автоматическая синхронизация численности;
- `supabase/survey_schema.sql` — таблицы сотрудников, волн, участия и карточек HRBP;
- `supabase/survey_wave_creation.sql` — связь опросов с общим реестром и ручное создание волн;
- данных хранятся в Supabase;
- графики строятся через Chart.js.

## Локальный запуск

```powershell
python -m http.server 4174
```

Затем откройте `http://127.0.0.1:4174/`.

Перед использованием раздела текучести выполните `supabase/turnover_schema.sql`
и затем `supabase/employee_roster.sql` в SQL Editor проекта Supabase.

После создания таблиц откройте `turnover.html` и нажмите **«Сотрудники»**.
Численность отделов рассчитывается автоматически по активным сотрудникам.
Увольнение уменьшает численность отдела, а добавление сотрудника — увеличивает.

Для раздела опросов выполните `supabase/survey_schema.sql`, а затем
`supabase/survey_wave_creation.sql`. После этого откройте `surveys.html`,
войдите в Supabase Auth и нажмите **«Новая волна»**. Можно указать название,
дату проведения, дедлайн и комментарий, выбрать весь отдел и снять отдельных
сотрудников. Созданная волна появится в журнале проведённых опросов.
Если `survey_wave_creation.sql` ещё не выполнен, интерфейс использует совместимый
режим записи через существующие таблицы; SQL-миграция дополнительно связывает
реестр с опросами, сохраняет комментарии и делает создание волны атомарным.

Пароль общего экрана дашборда не создаёт сессию Supabase. Для каждого сотрудника,
которому нужен доступ к опросам, создайте отдельного пользователя в
**Supabase → Authentication → Users**: укажите рабочую почту, временный пароль
и включите подтверждение пользователя. На странице опросов сотрудник входит по
этим почте и паролю. Одноразовые письма для входа не используются.

Пароли сотрудников нельзя хранить в GitHub, HTML или JavaScript. Создавайте их
в Supabase Authentication и передавайте сотрудникам по защищённому каналу.

CSV остаётся доступен для массовой исторической загрузки: сначала волны,
затем участие. Отдельный импорт сотрудников нужен только для людей, которых нет
в общем реестре.

Правило раздела: сотрудник попадает в рабочий список, когда текущая волна
пропущена, предыдущая волна также пропущена, а в трёх более ранних волнах
завершено не меньше двух ответов. Это сигнал для нейтрального check-in, а не
оценка лояльности и не основание для автоматического кадрового решения.

## Публикация

Сайт публикуется из ветки `main` через GitHub Pages.

## Важно про безопасность

Текущая проверка пароля выполняется на стороне браузера и не является полноценной
аутентификацией. Доступ к данным должен дополнительно ограничиваться политиками
Supabase Row Level Security. Для рабочего HR-контура с зарплатами, именами
сотрудников и кадровыми решениями рекомендуется перейти на Supabase Auth или
другой серверный механизм авторизации.

Политики из `turnover_schema.sql` сейчас разрешают чтение и запись для `anon`,
чтобы новый раздел заработал без дополнительной настройки. Это допустимо только
для тестовых данных. Перед загрузкой реальных кадровых данных нужно включить
Supabase Auth и заменить эти политики доступом только для `authenticated`.

Исключение — `survey_schema.sql`: его политики сразу разрешают доступ только роли
`authenticated`. Страница `surveys.html` намеренно не открывает имена сотрудников
через публичный ключ `anon`. Для работы с реальными данными нужно настроить
Supabase Auth и получить авторизованную сессию.
